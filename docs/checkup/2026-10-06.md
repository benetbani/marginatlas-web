## Verdict

The product's rails are sound and its honesty machinery is the best thing in it; what the goal asks for is mostly risk the
launch has not met yet. The SaaS layer was built in one night and is switched off, and its first real reader would find three
faults before any feature is missing (a fourth, feared from the migration files, measured false: the live database refuses the
public key's writes on all 13 tables, so row level security is on there though no file says so): the billing table keeps one row per account,
so an event for an old subscription can drop a paying reader to free and a changed email makes a second account that fails
every retry; the public data API returns figures the paywall locks on the pages; and the middleware never refreshes a session.
Around it, the structure has grown faster than it has been pruned: 245 gates (155 seventeen days ago) take 1,335 s serially,
the typecheck still reads 3,031 icon declarations and 196 scratch files because the last checkup's two fixes never merged, 23%
of the source (196 files, 43,344 lines) is reachable only from `/dev` review routes that production still builds, 12 files are
reachable from nothing, and 15 dependencies are imported by nothing, unchanged since 2026-09-19. The home page holds one
promise the site cannot keep (a "free report" PDF that does not exist) where his ruled ask ("notify me when my place reaches
this depth") belongs.

## Findings, ranked (his goals: launch with Pro on, honest figures, his time on judging; then certainty; then cost)

### 1. The migration files do not say what the live database enforces (security, structure)
- Measured: the migrations `db/migrations/2026-08-16-newsletter-source.sql`, `2026-08-16-corrections.sql` and
  `2026-05-24-deepening-schema.sql` never enable row level security. Live, the public anon key reads 0 rows of each form table
  (`contact_messages` holds 7 by the service key), and an insert sent with the public key and its required columns null is
  refused with 42501 on all 13 tables PostgREST describes (`node scratchpad/_rls_write_probe.mjs`: it cannot write a row, since
  a null in a required column fails either way; 23502 would have meant writable). So the live tables are protected and the
  files are wrong; the next table made from a file would not be. First drafted from the files alone as "readable today": the
  measurement corrected it.
- Change: a migration file that enables it on every table the files create, harmless where it is already on, so the files
  match the database; a gate holding that a migration which creates a table enables it. Kind: **change** (the file and the
  gate); applying it is **owner** (LAUNCH-SWITCHES row 2).

### 2. Billing keeps one row per account (money, trust)
- Measured: `subscriptions.user_id` is the primary key and the webhook upserts on it (`db/migrations/2026-10-05-pro-subscriptions.sql:10`,
  `src/app/api/stripe/webhook/route.ts`); the account is found by email on every event (`stripe_sync.ts`); checkout never
  passes an existing customer nor checks for an existing plan; no event is recorded; a caught failure reaches only the console.
- Change: resolve the account by Stripe customer first; on every event re-derive the reader's state from all of the customer's
  subscriptions (order-independent, idempotent); a `billing_events` table (migration file) for the audit trail; Sentry on
  failure; checkout sends a Pro reader to the portal and reuses the customer; a dry-run reconcile script. Kind: **change**.

### 3. The public data API returns locked figures (money)
